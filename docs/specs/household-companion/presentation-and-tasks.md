## 2. 呈现层负责决定“怎样让人理解”

`PresentationPlanner` 是 bot-server 内的职责边界，输入包括用户意图、回答内容、工具证据、当前参与者、设备能力、互动状态和家庭偏好；输出可执行的呈现计划。
它不要求每个简单回答多串行调用一次 LLM：固定应答采用模板，普通问题由主模型在同一次生成中输出内容和计划，复杂分步演示才按需要调用专门规划。

| 场景 | 适合的呈现 | 正确性依据 |
| --- | --- | --- |
| 英语单词怎么拼 | 清晰单词、逐字母高亮、发音与例句，可重播 | 文字与发音来自同一个已冻结片段；词典 / 发音素材保留来源 |
| 汉字怎么写 | 田字格、逐笔动画、笔画名称、暂停和下一笔 | 有来源、允许使用的笔顺数据；不能让图像模型猜笔顺 |
| 数学、物理概念 | 分步公式、坐标图、受力图或可控参数演示 | 数据和公式由可校验的结构化结果驱动，Mac 确定性渲染 SVG / 图表 / 帧序列 |
| 人文知识、家庭计划 | 时间线、地图、照片、事件关系与简短讲述 | 搜索或家庭原始记录的来源、时间和不确定性随素材保存 |
| 故事、陪伴、共同创作 | 表情、插画、声音、简短动画 | 创作插画可用已配置的生成能力；不得把未配置模型显示为可用 |
| 找一段音乐或视频 | 标题、来源、时长、字幕、播放 / 暂停入口 | 先核实素材可访问、格式可播放和使用范围；保留原链接和片段时间 |

不强制每轮都出现图片。呈现复杂度应匹配任务：一句回答可直接说；需要比较、观察或练习时才展开图文和步骤。家庭做饭、旅行安排、找照片、讲故事、打印资料与教育问题使用相同的任务和呈现基础。

### 2.1 四类对象分别存储

以下说明内部领域对象，不是将整张表作为设备 payload。源码类型位于 `brain/contracts.rs`、`presentation.rs`、`artifacts.rs` 和 `tasks.rs`；设备 wire 只接纳经 `presentation.segments.v1` 协商的有界字段，见 [v3 协议](../../../shared/mac-brain-v3.md) 与 [固件接线记录](../../../firmware/HOUSEHOLD_INTEGRATION.md)。

| 对象 | 最少信息 | 约束 |
| --- | --- | --- |
| `PresentationPlan` | `presentation_id`、版本、`task_id`、`conversation_turn_id`、有序片段、所需能力、完成条件 | 描述要表达的内容和依赖，不包含任意 HTML / JavaScript 或逐帧眼睛 / 电机命令 |
| `PresentationSegment` | 稳定片段 ID、speech、caption、visual、expression、必需 / 可选素材、同步点、停留 / 交互策略、降级方案 | 冻结后才进入素材制作；修改创建新版本并撤回旧版本播放权限 |
| `Artifact` | 不可变资产 ID、内容摘要、类型、尺寸 / 时长、来源、生成参数、计划 / 片段版本、保留策略 | 资产可重放 / 重印；当前播放 token 不是资产身份。屏幕缩略图与打印原稿分别保存 |
| `PlaybackJob` / 回执 | `playback_id`、`output_lease_id`、`activation_id`、实际 runtime token、片段与资产版本、序号、设备相对时间、状态 | 只在当前许可内调度播放；收到、首次绘制、声音开始、完成、停止、失败分别记录 |

家庭日记录引用计划、资产、任务和回执。**生成过、传输过、设备绘制过、音频实际输出过、外部操作执行过是不同事实。**
硬件播放完成也不等于有人听见或理解；学习记忆只能使用后续回答等明确证据。

### 2.2 冻结内容后并行制作，按依赖逐段播放

1. 主模型 / 模板产出一个语义完整的短片段，校验内容、来源和设备能力。
2. 冻结片段文字与版本，TTS 和相应图片 / 动画准备才可并行。需要根据数据重新计算结论时，先完成计算再冻结。
3. 不依赖图片的第一段解释可以先发；“看这里的红色箭头”必须等待对应素材的**首次实际绘制回执**。
4. 每个片段有独立就绪 / 失败状态。必要图片失败时该任务是部分完成，并明确说明；可选插画失败不抹掉已完成解释。
5. 声音、字幕高亮、表情和动画采用设备播放时钟 / 样本位置的相对调度。Mac 墙钟与 ESP uptime 不直接相减；回执用稳定 ID 关联。
6. 媒体阻塞时保持可用停止入口；超时后释放有界缓冲、撤回该播放许可，允许文本或 Mac 展示降级。

当前 `image_prepare` 对结论的改写应移入语义准备阶段，或者形成明确的新片段版本。不能让已经合成的旧文字音频搭配改写后的新图。
分段输出先用有界完整句 / 步骤实现；不把未完成的模型 JSON token 直接发给固件执行。

### 2.3 屏幕和声音是一个体验

Bot 用本地插值表现倾听、思考、回答等状态。呈现内容时，眼睛可缩小为状态提示，给文字 / 图片足够面积；完成后由本地 runtime 恢复脸部布局。
文字保留阅读时间，用户可“上一页 / 下一步 / 再说一次 / 放大到 Mac”。没有新授权时，只保留静态阅读状态，不能因内容仍显示而继续采集声音。
表情是语义提示，不要求模型逐帧操纵瞳孔；当前硬件没有电机，不生成假动作。

重访使用保存的计划和不可变资产，不为“再看看刚才那张图”重新生成一张不一样的图。
音视频完成后保留标题、出处、片段位置和必要缩略图；原始媒体是否长期保留由单独的容量 / 保留策略决定。

## 3. Mac 制作媒体，Bot 按实际能力播放

Mac 负责检索、读取、字体排版、确定性绘图、缩放、转码、TTS、缓存和大文件管理；Bot 只承担经协商的有界解码 / 播放、字幕、轻量表情和立即停止。

- 复用 [FFmpeg filters](https://ffmpeg.org/ffmpeg-filters.html) 处理缩放、帧率和字幕等素材准备。
- 优先评估 Espressif [esp_player](https://github.com/espressif/esp-gmf/blob/main/packages/esp_player/README.md) 的媒体管线与同步，以及 [esp_video_render 示例](https://github.com/espressif/esp-gmf/blob/main/packages/esp_video_render/examples/video_render/README.md) 的 LCD / LVGL 组合，接入现有唯一音频 owner，不能另开声卡播放器。
- 能力协商包括编解码格式、分辨率、最大资产 / 缓冲、播放控制、同步能力、取消时延和当前资源预算。上游支持某格式不代表本板已验收；不预设 H.264 硬解或固定视频帧率。
- [ESP32-S31 JPEG 官方文档](https://docs.espressif.com/projects/esp-idf/en/v6.1.1/esp32s31/api-reference/peripherals/jpeg.html)明确同一时刻 codec engine 只能编码或解码。相机编码与屏幕视频解码必须排队 / 分时，必要时主动降低相机或媒体负载，不能让感知任务无限占用播放器资源。
- 先交付文字、静态图与分段语音，再交付有界动画 / 短视频。对超出设备能力的媒体，在 Mac 展示并在 Bot 给出明确入口；这不能计作 Bot 视频验收通过。
- 媒体仅投递到当前授权的输出目标。断线重连后恢复内容需新输出许可，旧下载 / 播放消息不能借新 token 重新生效。

这些是组件选择与资源约束；本次文档工作不安装媒体依赖，也不声称完成实板性能测试。

## 4. 先答应、报真实进度、再给出可用结果

### 4.1 应答不启动额外模型调用

本地完整唤醒后可短答“我在”，继续复用现有 104 条离线语音及表情。任务收到后，如果结果尚未就绪，再按任务和时间环境选择短应答；快速结果到达就取消尚未播放的“等一下”。
应答协调器记录本次激活最近播过什么，避免连续“我在 / 我在 / 好的 / 我在想”。夜间、静音和用户设置沿用 runtime 的权威设置；选择时间性问候不能声称识别了未确认的家庭成员。

建议先作为**可调整的体验目标**：耗时任务在约 5–8 秒内给一次有意义的状态；后续口头进度通常至少间隔 15–20 秒，或由确实需要告知的阶段变化触发。
这些数值不是现有延迟测量，也不是所有阶段统一的超时。图像生成、检索、模型响应、打印分别设定时限与无进展判断。

### 4.2 进度必须来自执行证据

| 真实事件 | 可以说 / 展示 | 不能据此推断 |
| --- | --- | --- |
| 检索适配器开始请求 | “我正在查资料” | 已经找到可靠答案 |
| 图片生成或绘图任务确实开始 | “我正在准备这张图” | 图片已经生成 / 显示 |
| TTS 制作开始 | “正在准备声音”的轻量状态 | 设备已经发声 |
| 所需权限 / 参数缺失 | 具体需要的选择或现有授权提示 | 用模糊“处理中”无限等待 |
| 心跳正常但阶段无进展 | 服务仍连接；超过阶段阈值后说明耗时 | 百分比进度或任务仍有效推进 |
| 外部工具失败 / 超时 | 哪部分完成、哪部分失败、可用结果 | 操作失败前一定没有产生副作用 |

OpenCode 的工具开始 / 进度 / 成功 / 失败事件可映射到稳定任务阶段，不向用户朗读内部推理。
按 [OpenCode API](https://opencode.ai/docs/api) 与实际目标版本核对事件；事件流不是可靠重放日志，bot-server 要保存自身任务事件，并在重连时读取状态 / 结果进行核对。
没有工具类型证据时只说“我还在处理”，不能凭模型文本冒称正在搜索或绘画。进度序号、阶段、任务 ID 和取消代数一起校验；旧任务状态不得覆盖新任务。

### 4.3 播放目的决定完成后的行为

| 拟议 `purpose` | 完成后允许发生的动作 |
| --- | --- |
| `wake_ack` | 沿用当前唤醒收音流程，尾音清理后才允许采集 |
| `task_ack`、`progress` | 只完成本次播报，不结束任务；现有端仍等待呈现完成。RA-04 目标在所需回执齐全后另用协商的前台完成事件释放本轮，不能仅凭 ACK 开启追问 |
| `content` | 推进同一呈现计划的下一片段；按该片段策略等待用户或素材 |
| `final` | 必要内容与真实播放条件满足后，才按已有策略准备追问 |
| 设置试听 | 继续使用设置专用 lease，不创建家庭对话或收音权限 |

Stop / 取消 / 失效时同时撤回未播放应答、进度和内容的输出许可，已排队素材不能重新标记为当前 token。
如果长任务完成时当前互动已结束，保存结果供下次查看；只有事先明确配置或本次请求授权了完成提醒，才可以重新通知。不能因任务后台完成而自行开启麦克风。

## 5. 持久任务与当前互动分开

`task_id` 表示一件工作，关联家庭、发起源 `conversation_turn_id`、能力、输入版本、产物、状态和证据。
`activation_id` 是短期互动授权；`output_lease_id` 是一次呈现许可；`daily_conversation_id` 是家庭日记录。三者都不是任务的生存期。
任务可以跨天或设备离线后继续完成，但不能拿旧许可播放结果。

任务建议状态为 `queued / running / awaiting_input / succeeded / partial / failed / cancel_requested / cancelled / unknown`。
外部副作用适配器保留自己的细分状态；取消请求不等于外部操作已撤销。播放另外记录准备、已收、开始、完成、被打断、失败，不能用 `task.succeeded` 代替硬件播放完成。

### 5.1 调度与 OpenCode

1. Mac 先持久化已接收输入、任务和取消代数，再调度工作；服务重启可恢复或核对任务，不能只保存在 `tokio::spawn` 的内存闭包里。
2. 同一家庭前台 OpenCode 会话有顺序输入队列，保留“刚才那个”的指代关系。长工具 / 媒体工作移到受管理任务；新的短问题可以进入前台。
3. 若任务需要单独 OpenCode 工作会话，明确建立与家庭日会话的父子 / 任务关联，回传结构化结果；不能直接启用尚未桥接权限和取消的子代理 / Code Mode。当前限制见[能力清单](../../opencode-capabilities.md)。
4. ASR、声纹、TTS、检索、素材制作、后台记忆有明确并发和模型内存预算；前台交互优先，后台整理可检查点后暂停。
5. 取消分为停止当前播放、停止本次收音 / 回答、取消某个后台任务和停止服务。默认“停止”及时停当前体验；已经提交外部操作的撤销由适配器另行核对。
6. 同一任务重试使用幂等键；跨网络错误先核对外部结果，避免打印、写文件等副作用重复执行。任务日志记录操作意图、实际回执和未知状态。

### 5.2 独立结果收件箱与能力操作 — 2026-11-25 目标

任务成功、结果持久化、内容已发送和设备已播放分别记录。当前回答完成后可释放输入槽，任务继续执行；结果进入持久收件箱，通过当前听众/来源有效性、安静策略、激活和输出许可检查后才交付。用户正在说话、互动已结束或设备离线时保留结果，不抢占或自动开麦。

从自然语言发起的任务与记忆/提醒等动作统一经过[能力服务](../responsive-assistant/capabilities.md)，绑定真实 source 和幂等键。received 只表示接收；任务/操作可靠保存后才报告 accepted；效果完成需适配器回执；重启后的 unknown 先核对外部状态。

具体状态、迁移和兼容见 [RA-04](../responsive-assistant/steps/ra-04-task-delivery.md)、[RA-06 任务控制](../responsive-assistant/steps/ra-06-context-and-task-control.md)和 [RA-09 恢复](../responsive-assistant/steps/ra-09-recovery-and-migration.md)。这是后续目标，尚未由本次文档修改实现。

### 5.3 打印作为首个完整的“做事情”能力

评估 macOS [NSPrintOperation](https://developer.apple.com/documentation/appkit/nsprintoperation/) 的系统打印入口，
以及 [CUPS](https://www.cups.org/doc/options.html) 的提交 / 队列接口，由专门适配器负责枚举打印机、提交和查询；
[lpstat](https://www.cups.org/doc/man-lpstat.html) 可用于队列状态查询。具体采用方式以目标 Mac 和打印机实测为准。
如果某种入口不能返回可追踪的任务标识，必须降低结果确认级别，不能仅凭系统窗口关闭或 API 返回成功就标记打印完成。

| 阶段 | 保存的事实 | 对用户的表述 |
| --- | --- | --- |
| 产物准备 | PDF / 图片不可变资产、摘要、预览、页数 | “资料已经准备好” |
| 意图就绪 | 用户明确打印请求或已配置的适用许可、目标打印机、份数、纸张等 | 已有必要信息就执行；仅询问缺失的关键项，不重复要求已给过的授权 |
| 正在提交 | 任务幂等键、提交尝试 ID、产物版本、目标和参数 | “正在发送到打印机” |
| 队列接收 | CUPS / 系统返回的真实 job ID 与状态 | “已经加入打印队列” |
| 后续状态 | 排队、处理中、设备报告完成 / 失败 / 取消，或无法确认 | 只按实际回执说明；队列已收不等于纸已经打印出来 |

同一打印意图重试不得换幂等键。提交超时而结果未知时，先按 job ID / 已记录尝试核对队列，不能直接再打一份。
用户明确说“再打一份”才建立新的打印意图。请求取消后，已打印的页不能回滚；记忆中保存取消请求与实际结果，不能只写“已取消”。
语音识别为某位成年人不是执行授权本身；使用既有设置和明确操作意图。打印预览、屏幕展示和实际打印必须引用同一内容版本，不能执行前又悄悄重新生成。

## 6. 开发步骤与验收入口

下面保留本规范的分工及待执行验收，完整前置关系以[实施计划](implementation-plan.md)为准。源码开发完成，待测试；HC-15 的手工场景没有执行，不创建 CI。

当前服务端冻结计划后按片段派发，设备仅在文本/图像真实 flush、实际音频完成及停留结束后回报 `presentation.segment.report`；失败不能冒充完成。任务 ACK/进度可以在同一 runtime 内用递增 `presentation_index` 换新冻结计划和新 lease，但不能抢占播放中的片段。无有效输出许可、来源过期或预算不足时，完整结果留在 Mac，不自动唤醒设备或截掉尾部后宣称完成。

Mac 已接确定性图解、受控音视频准备、素材回看与 PDF 打印；笔顺使用可选的真实数据源，缺失时只显示普通字形。设备采用 JPEG 帧回压播放，单帧 ≤480×272/65,536 字节、runtime 总计 64 段，服务端短片 ≤12 秒/60 帧预算；固件连续墙钟预算 15 秒。回压可能使短片超时，这些上限不是实测 5 fps 或音画同步效果。创意生成服务、模型和数据集未配置时如实降级，不能把场景表中的目标能力全部当作已配置服务。
